# API contracts — stage 02 output

Two upstream APIs, both called **only by the Go server** (the browser never
talks to RunPod or the LLM). Field names for RunPod are confirmed against
github.com/sruckh/minmaxmusic3-serverless; the async surface is RunPod's
platform API (verify live in stage 08).

## A. RunPod worker (inference)

### A1. Submit — `POST {RUNPOD_ENDPOINT}/run`

Header `Authorization: Bearer {RUNPOD_API_KEY}`. Body:

```json
{"input": {
  "input": "<lyrics with section tags, each tag alone on its line>",
  "instructions": "<style caption: Global Metadata / Vocal Details / Arrangement>",
  "audio_duration": 30.0,
  "seed": 7
}}
```

Field rules: `input` non-empty, tags on own lines; `instructions` non-empty,
tokenized prompt ≤ 5,000 tokens; `audio_duration` float 10–300 (upper
bound); `seed` optional int (omit ⇒ worker default).

Response `< 2 s`: `{"id": "<runpod-job-id>", "status": "IN_QUEUE"}`.
Client timeout 30 s (submission only enqueues — this guards a hung
connection, not the render).

### A2. Poll — `GET {RUNPOD_ENDPOINT}/status/{id}`

Same auth. Response: `{"id", "status", "output"?, "error"?}` with
`status ∈ IN_QUEUE | IN_PROGRESS | COMPLETED | FAILED | CANCELLED`.

- Poll cadence: 3 s for the first minute, 10 s after; **give up at 15 min**
  ⇒ job `failed(timeout)`; one `POST /cancel/{id}` best-effort before that.
- `COMPLETED` ⇒ `output` (schema A3). `FAILED` ⇒ `error` stored verbatim
  (capped 2 KiB) and shown through the error taxonomy.

### A3. Completion payload (`output`)

```json
{"delivery": "s3" | "base64",
 "audio_url": "…?X-Amz-Signature=…", "url_expires_in": 86400,
 "format": "wav", "sampling_rate": 32000, "channels": 2,
 "duration": 30.0, "num_frames": 750, "seed": 7,
 "model": "MiniMaxAI/MiniMax-Music3", "engine": "diffusers"}
```

- `delivery=s3`: fetch `audio_url` **immediately** (expiry is up to 24 h but
  treat as 1 h); store bytes locally; never hand the presigned URL to the
  browser (it may contain bucket metadata; our `/audio/{song-id}` serves the
  stored copy).
- `delivery=base64`: inline audio ≤ 18 MB ⇒ ~105 s max audio; decode and
  store. Treat as degraded mode: log it.
- Persist a `songs` row whatever the delivery mode.

### A4. RunPod error taxonomy

| Class | Signal | Permanent? | Job transition | User sees |
|---|---|---|---|---|
| Config | `RUNPOD_ENDPOINT`/`KEY` unset | yes | failed(config) | "Service misconfigured" (admin copy) |
| Rejected | HTTP 400/401/403/404 | yes | failed(rejected) | "Generation request was rejected" + retry |
| Transient | HTTP 429/5xx, network | no — retry next tick (max 3) | stays queued/running | "Still working…" |
| Schema | JSON decode mismatch | yes | failed(schema) | "Service response changed" |
| Job failed | status FAILED | yes | failed(worker) + stored `error` | reason, sanitized |
| Timeout | 15 min poll budget | yes | failed(timeout) | "Took too long" + retry |

## B. LLM assistant

`POST {LLM_BASE_URL}/chat/completions` (OpenAI-compatible),
`Authorization: Bearer {LLM_API_KEY}`. Model: `{LLM_MODEL_ID}` — all three
from Infisical env dev, server-side only.

Body: `{"model": "{LLM_MODEL_ID}", "messages": [{"role": "system",
"content": <shared/llm-assistant-system-prompt.md verbatim>}, {"role":
"user", "content": <rough idea, ≤ 4,000 chars>}], "max_tokens": 2000,
"temperature": 0.8}`. Client timeout 60 s, one retry on network error only.

Response: standard `choices[0].message.content`. Parsing contract: the
assistant is required (system prompt Step 4) to end with a fenced JSON block
of exactly `{"input", "instructions", "audio_duration", "seed"}`. Parser:
take the **last** fenced JSON block; validate `input`/`instructions`
non-empty strings, `audio_duration` clamped 10–300, `seed` int-or-null.
Parse failure ⇒ assistant error class, HTTP 502 `{"error":
"assistant-unparseable"}` — the form stays untouched and usable.

Assistant error taxonomy: 400/401 ⇒ permanent "assistant-unavailable"
(503); timeout/network ⇒ "assistant-timeout" (504); parse ⇒ 502. The panel
shows next-step copy; the generation form is never blocked.

## C. Job state machine (app-side)

`queued → submitted → running → succeeded | failed` (+ `cancelled`).
Worker idempotency: a row with a `runpod_id` is never re-submitted; state
transitions are single UPDATE … WHERE state=<expected> (compare-and-set).
Restart recovery: on boot, rows in `submitted`/`running` resume polling
(they have `runpod_id`); rows in `queued` resubmit.
